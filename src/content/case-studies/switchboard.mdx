<CaseSection title="Investigating a customer change">

Changing a production webhook endpoint means deciding where customer events will be sent. An incorrect change could interrupt delivery or send those events to an unauthorized destination. Before an engineer updates the configuration, they need to establish what the customer requested, whether it’s permitted, and who must approve it.

Switchboard is an independent AI change-management system deployed on AWS. Python, FastAPI, and LangGraph investigate requests and prepare source-backed findings. The application controls independent approval, execution, and delivery verification. The company and customer records are synthetic; the deployed workflow makes real model calls and sends signed HTTP requests to a separate receiver.

In the main scenario, Acme asks to replace its production webhook endpoint. The investigator reads the ticket, checks the requester against authorized customer contacts, and compares the proposed destination with registered endpoints. It must use the current policy, which requires approval from a technical lead assigned to the customer who did not propose the change.

The application supplies the employee’s identity, and the agent’s tools check customer access before returning records. An employee assigned to Acme cannot retrieve Globex’s configuration through the investigator. Before saving a proposal, application code checks the proposed change against current business records.

</CaseSection>

<CaseSection title="Running the workflow on AWS">

CloudFront serves the Next.js website and routes API requests to separate AWS Lambda functions. The website uses the Lambda Web Adapter; the FastAPI API uses Mangum. A native Python worker handles investigations delivered through SQS.

LangGraph coordinates the AI investigation: retrieving evidence, preparing a structured report, reviewing policy claims, and revising findings when needed. Step Functions coordinates the longer business workflow. It starts the queued investigation, receives the worker’s completion callback, and waits for independent approval, explicit execution, and verification.

Progress lives in DynamoDB, so visitors can reopen a job after navigating away. The worker saves validated output before publishing completion, allowing retries to reuse it. SQS handles transient retries and sends exhausted messages to a dead-letter queue. EventBridge Scheduler runs recovery checks for pending submissions and failed deliveries.

</CaseSection>

<CaseSection title="Checking the agent’s conclusions" media>

A correct recommendation can still contain an inaccurate explanation. The policy reviewer compares the report’s claims with the current workspace policies and cites excerpts for questionable claims. Application code checks that each excerpt occurs in its cited source, allows one report revision, and evaluates it again. Reports that still fail validation are rejected before a proposal is created.

Missing evidence, confirmed violations, and requirements that apply at approval or execution receive different statuses. The reviewer must distinguish a rule from a customer record and preserve conditional permissions. For example, a policy that permits restoration only when the approved recovery plan allows it must not become a blanket ban or unconditional permission.

Live-model evaluations cover valid requests, unauthorized requesters, unregistered destinations, conflicting policy versions, cross-customer access, and instructions embedded in tickets that attempt to override policy. Separate policy cases exercise source grounding and faithful interpretation. Deployed workflow checks also verify approval, stale configuration rejection, duplicate execution, delivery receipts, and workspace isolation. These are bounded test cases, rather than an estimate of accuracy on unfamiliar requests.

The evaluator can quote a policy accurately and misinterpret it, so application code independently enforces authorization. A human reviewer can open source records alongside the findings and inspect the evidence captured during the investigation, even if the underlying configuration has since changed.

<CaseSection title="Executing and verifying an approved change">

By the time a proposal reaches execution, the customer may have revised its instructions, an employee may have lost access, or another engineer may have updated the endpoint. Switchboard checks current authority, approval, the permitted change window, and configuration again before applying the change.

DynamoDB conditional transactions commit the configuration update and its execution receipt together. A proposal expecting version 7 is rejected if another change has advanced the configuration to version 8. If an approved update succeeds but the browser loses the response, a retry returns the saved receipt without applying the change again.

Verification checks the active endpoint and sends a signed synthetic event over HTTP to a separate Lambda receiver. The receiver persists its own receipt. Switchboard checks the destination, event ID, and payload hash against that receipt before confirming delivery and closing the ticket. A timeout is inconclusive; failure or uncertainty requires manual intervention. The application does not perform automatic business rollback.

I verified the deployed workflow with real model investigations and real signed delivery. Stale proposals left the endpoint unchanged, completed execution retries returned the original receipt, and delivery verification matched the receiver’s independently saved result.

</CaseSection>

<CaseSection title="Deploying and operating the system">

CloudFormation defines the application infrastructure, Lambda configuration, and live release aliases. GitHub Actions builds and deploys releases using OIDC to assume an AWS role, without storing long-lived AWS access keys in GitHub. IAM roles limit each function to the records, queues, and operations it needs; the model credential is held in an encrypted Parameter Store value available to the worker.

CloudWatch provides structured logs, a dashboard, and alarms for failed workflows, queue backlogs, dead-letter messages, and delivery failures. OpenTelemetry and X-Ray tracing connect sampled requests across components. Operational emails summarize what failed and link to investigation and recovery views. Logs retain validation reasons so rejected reports can be diagnosed.

The live model connection uses DeepSeek directly. A Bedrock adapter is also implemented and tested, but Bedrock is not the model provider used by the public deployment.

</CaseSection>
