<CaseSection title="Checking customer change requests">

Switchboard helps a team investigate and carry out customer changes. In the demo, a customer asks to change where their system receives event notifications. Sending those notifications to the wrong place could expose data or interrupt a service.

I built a Python and LangGraph agent that reads the request, checks customer records and company policies, and prepares a report with links to its evidence. An authorized employee must approve the proposal before anyone can apply the change.

The demo uses fictional company and customer records. Investigations call a real AI model through Amazon Bedrock, and delivery checks send signed test events between controlled AWS endpoints.

<CaseSection title="From request to confirmed delivery" media>

The AI can investigate and recommend a change. Approval must come from an authorized employee who did not submit the proposal.

<figure className="switchboard-architecture" aria-label="Switchboard change workflow">
  <ol>
    <li>
      <strong>Investigate the request</strong>
      <span>Check who requested the change, where events will go, and which policies apply.</span>
    </li>
    <li>
      <strong>Review and approve</strong>
      <span>Another authorized employee reviews the evidence and decides whether to approve.</span>
    </li>
    <li>
      <strong>Apply the change</strong>
      <span>Recheck permissions and the current configuration before making the update.</span>
    </li>
    <li>
      <strong>Confirm delivery</strong>
      <span>Send a test event and check that it arrived at the new destination.</span>
    </li>
  </ol>
</figure>

Reports cite the records and policies behind their findings. A second AI review checks the policy interpretation, and application code checks the quoted evidence. Reports that fail these checks are rejected before a proposal is saved. Access rules also keep each employee's investigation limited to their assigned customers.

Before applying an approved change, Switchboard checks that the configuration has not changed since the proposal was prepared. Repeating a completed request returns its saved result without applying the change twice.

<CaseSection title="Built on AWS">

The Next.js website and FastAPI backend run on Lambda, with CloudFront serving the site. Step Functions tracks the workflow as it moves through investigation, approval, execution, and delivery checks. SQS queues investigation jobs and retries temporary failures. DynamoDB saves progress and results so visitors can return to a request later.

AWS SAM and CloudFormation define and deploy the application. GitHub Actions publishes updates, while CloudWatch logs and alerts and X-Ray traces help diagnose failures.

The source repository covers the architecture, access controls, and tests in more detail.

</CaseSection>
